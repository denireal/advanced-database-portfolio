# Execution Plans: Luma Polytechnic (`lumapoly`)

**Portfolio 2:** Query Processing and Optimisation | **DBMS:** MySQL 8.0.46 (InnoDB)
Queries are in `sql-queries.sql` (Parts 2 and 3). Evidence images: `query-results.png`, `indexing-optimisation-evidence.png`. Analysis: `brief-performance-analysis.md`.

## 1. How these plans were captured

- **Tool:** `EXPLAIN ANALYZE`, which runs the query and prints the plan with *measured* time and row counts next to the optimiser's *estimate*. The tabular `EXPLAIN` is used where access type and key choice are the point.
- **Data:** 40,000 students, 960,000 registrations, 784,000 scores, 2,800 course offerings (generated by Part 0 of `sql-queries.sql`).
- **Machine:** 1 vCPU, 4 GB RAM, 1 GB InnoDB buffer pool. Timings in this file are medians of 3 to 5 runs after one warm-up run. Your numbers will differ, but the plan *shapes* should match.
- **Readability edit:** the optimiser's cost figures are removed and the row estimate is shown as `[est rows=N]`. Everything else is raw output.

### Reading the plans

| Fragment | Meaning |
|---|---|
| `Table scan on X` | Reads every row of X (`type: ALL`) |
| `Index range scan` / `Index lookup` | Uses a B-tree index to reach only the matching rows |
| `Covering index lookup` | Answered from the index alone, with no table access (`Using index`) |
| `Single-row index lookup ... PRIMARY` | Point lookup by primary key |
| `Aggregate using temporary table`, `Materialize` | An intermediate result is built before the next step |
| `re-planned for each iteration` | A range condition is re-evaluated for every outer row (expensive when the outer side is large) |
| `[est rows]` vs `actual rows` | A large gap means poor statistics or a mis-estimated condition |
| `actual time=a..b` | `a` = first row (ms), `b` = last row (ms), per loop. Node cost is roughly `b x loops` |

## 2. Summary of plan changes

| Query | What the baseline plan showed | Change | Plan after | Median before | Median after |
|---|---|---|---|---|---|
| Q1 transcript | Index lookup on `uq_registration`, then primary-key lookups | None needed | Same | 1.7 ms | 1.6 ms |
| Q2 GPA ranking | 156,800 rows joined to `students` and range-joined to `grade_scale` before the top 10 were chosen | Late join, `grade_lookup`, covering index | Equality joins; 20,000 student lookups instead of 156,800 | 3,542 ms | 737 ms |
| Q3 course report | Already uses a covering index; volume-bound | None | Same | 574 ms | 612 ms |
| Q5 late drops | `Table scan` of 960,000 rows | Composite index `(status, registered_at)` | Covering index range scan, 1,372 est. rows | 267 ms | 2.7 ms |
| Q6 top scores | `Table scan` of 784,000 rows, 5,341 kept | Index on `total_score` | Index range scan, 5,341 rows | 190 ms | 3.2 ms |
| Q7 pass count | Table scan even though an index exists | None (optimiser is right) | Same | 215 ms | 223 ms |
| Q8 best per course | Dependent subquery run 8,000 times | Window function | One sort and one `RANK()` pass | 5,058 ms | 37 ms |
| Q9 CGPA risk | Reads all 784,000 scores, 9-way hash range join | Summary table | Index range scan on 397 rows | 6,656 ms | 0.5 ms |

**Reading it.** The optimiser pushed `term_id = 6` into the view, so only 400 offerings and 156,800 registrations are read, which is correct. The cost is *what happens to each of those 156,800 rows*:

- a primary-key lookup into `students` (156,800 loops) even though only the top 10 students are needed;
- a primary-key lookup into `grades` (156,800 loops);
- a **range join to `grade_scale`**, re-planned 156,800 times at about 0.012 ms each, which is roughly 1.9 s of the total.

The aggregate then produces 20,000 groups, from which only 10 rows are returned.

```
                                -> Aggregate using temporary table  (actual time=778..778 rows=20000 loops=1)
                                    -> Nested loop inner join  [est rows=113014] (actual time=0.112..583 rows=156800 loops=1)
                                        -> Nested loop inner join  [est rows=113014] (actual time=0.106..429 rows=156800 loops=1)
                                            -> Nested loop inner join  [est rows=113014] (actual time=0.0984..104 rows=156800 loops=1)
                                                -> Nested loop inner join  [est rows=400] (actual time=0.0446..2.1 rows=400 loops=1)
                                                    -> Table scan on c  [est rows=400] (actual time=0.0312..0.486 rows=400 loops=1)
                                                    -> Single-row covering index lookup on o using uq_offering (course_id=c.course_id, term_id=6)  [est rows=1] (actual time=0.00367..0.0037 rows=1 loops=400)
                                                -> Filter: (r.`status` = 'REGISTERED')  [est rows=283] (actual time=0.0451..0.234 rows=392 loops=400)
                                                    -> Covering index lookup on r using idx_reg_cover (offering_id=o.offering_id, status='REGISTERED')  [est rows=283] (actual time=0.0446..0.143 rows=392 loops=400)
                                            -> Filter: (g.total_score is not null)  [est rows=1] (actual time=0.00187..0.00194 rows=1 loops=156800)
                                                -> Single-row index lookup on g using PRIMARY (registration_id=r.registration_id)  [est rows=1] (actual time=0.00175..0.00177 rows=1 loops=156800)
                                        -> Single-row index lookup on gs using PRIMARY (score=g.total_score)  [est rows=1] (actual time=818e-6..841e-6 rows=1 loops=156800)
```

**Reading it.**

1. `students` is joined **after** aggregation: `loops=20000` instead of 156,800.
2. `grade_scale` is replaced by `grade_lookup`, an equality join on its primary key (`Single-row index lookup on gs using PRIMARY (score=g.total_score)`), about 0.0008 ms per row instead of 0.012 ms.
3. `registrations` is read with `Covering index lookup ... idx_reg_cover`, so no table access is needed for `student_id`.

| Step | Median | Gain over previous |
|---|---|---|
| Baseline (view) | 3,542 ms | n/a |
| 1. Aggregate first, join `students` last | 2,887 ms | 1.2x |
| 2. Equality join to `grade_lookup` | 1,249 ms | 2.3x |
| 3. Covering index `idx_reg_cover` | 754 ms | 1.7x |

**What remains.** 156,800 primary-key lookups into `grades` (about 0.28 s). That is the floor for computing GPAs from raw scores. Going lower would require a pre-computed summary (see Q9).

```
-> Limit: 10 row(s)  (actual time=637..637 rows=10 loops=1)
    -> Sort: pass_pct, c.course_code, limit input to 10 row(s) per chunk  (actual time=637..637 rows=10 loops=1)
        -> Table scan on <temporary>  (actual time=637..637 rows=400 loops=1)
            -> Aggregate using temporary table  (actual time=637..637 rows=400 loops=1)
                -> Nested loop inner join  [est rows=135370] (actual time=0.103..423 rows=156800 loops=1)
                    -> Nested loop inner join  [est rows=135370] (actual time=0.0956..103 rows=156800 loops=1)
                        -> Nested loop inner join  [est rows=400] (actual time=0.0474..2.28 rows=400 loops=1)
                            -> Table scan on c  [est rows=400] (actual time=0.0356..0.548 rows=400 loops=1)
                            -> Single-row covering index lookup on o using uq_offering (course_id=c.course_id, term_id=6)  [est rows=1] (actual time=0.00402..0.00406 rows=1 loops=400)
                        -> Filter: (r.`status` = 'REGISTERED')  [est rows=338] (actual time=0.0402..0.228 rows=392 loops=400)
```

**Reading it.** Both joins that matter are already index-driven: `uq_offering` finds the 400 offerings and `idx_reg_offering_status` is a *covering* lookup (no table access). The remaining cost is 156,800 primary-key lookups into `grades`, because the report must read every score of the term. This is volume, not a missing index, so I made no change.

**Is `idx_reg_offering_status` still needed?** After `idx_reg_cover` was added, the older index became a left prefix of it, so it looks redundant. MySQL's *invisible index* feature is the safe way to test a drop (Part 3.2 of `sql-queries.sql`), but a single comparison proved unreliable on this shared machine. I therefore alternated the two states (index present, index dropped and rebuilt) twice in one session:

| Round | Index present: Q3 / Q4 / Q2 (ms) | Index dropped: Q3 / Q4 / Q2 (ms) |
|---|---|---|
| 1 | 387.2 / 200.4 / 514.2 | 440.1 / 168.9 / 549.1 |
| 2 | 395.0 / 187.6 / 516.2 | 464.0 / 219.5 / 689.0 |

Without the index, Q3 was about 13% slower and Q2 was slower in both rounds (+7% and +34%); Q4 was mixed. The evidence does not justify dropping it, so **it was kept**. The first single comparison had suggested "no difference", which is why repeated alternating runs matter.

## 6. Q5: Late drops by day (composite index column order)


**Reading it.** `Table scan on registrations`: all 960,000 rows are read to keep 3 days of dropped registrations. There is no usable index because `status` and `registered_at` are not indexed.

### Three candidate indexes (forced with `USE INDEX` so they can be compared)

| Candidate | access `type` | `rows` (est.) | `Extra` | Median |
|---|---|---|---|---|

### After: `(status, registered_at)`

```

    -> Table scan on <temporary>  (actual time=1.42..1.42 rows=3 loops=1)
        -> Aggregate using temporary table  (actual time=1.41..1.41 rows=3 loops=1)

```

**Reading it.** The index is entered at `status = 'DROPPED'` and read only between the two dates, 1,372 estimated entries instead of 960,000. The rule is **equality column first, range column second**. With `registered_at` first, MySQL must read every entry for the week (about 136,000 to 161,000) and filter on `status` afterwards.

## 8. Q7: An index the optimiser rightly ignores

```sql
SELECT COUNT(*) AS passes, ROUND(AVG(ca_score),1) AS avg_ca FROM grades WHERE total_score >= 40;
```

**Plan with `idx_grades_total` available (tabular `EXPLAIN`):**

| table | type | possible_keys | key | rows | filtered | Extra |
|---|---|---|---|---|---|---|
| grades | ALL | idx_grades_total | NULL | 738344 | 50.0 | Using where |

`possible_keys` lists the index but `key` is `NULL`: the optimiser chose a full scan. About 76% of rows match, and `ca_score` is not in the index, so using it would mean roughly 600,000 index entries plus 600,000 random primary-key lookups.

**Forced with `FORCE INDEX` (1,210 ms vs 243 ms):**

```
-> Aggregate: avg(grades.ca_score), count(0)  [est rows=1] (actual time=1391..1391 rows=1 loops=1)
    -> Index range scan on grades using idx_grades_total over (40 <= total_score), with index condition: (grades.total_score >= 40)  [est rows=369172] (actual time=16.7..1328 rows=600097 loops=1)
```

**Reading it.** The forced plan reads 600,097 index entries and is about 5.0x slower. An index helps when the predicate is selective (Q6: 0.7%) and hurts when it is not (Q7: 76%).


## 11. Q10: Histogram statistics for an un-indexed column

```sql
SELECT COUNT(*) AS high_exam FROM grades WHERE exam_score >= 65;
```

**Before the histogram:**

```
-> Aggregate: count(0)  [est rows=1] (actual time=200..200 rows=1 loops=1)
    -> Filter: (grades.exam_score >= 65)  [est rows=258655] (actual time=1.62..200 rows=9577 loops=1)
        -> Table scan on grades  [est rows=776042] (actual time=1.55..164 rows=784000 loops=1)
```

**After `ANALYZE TABLE grades UPDATE HISTOGRAM ON exam_score WITH 64 BUCKETS`:**

```
-> Aggregate: count(0)  [est rows=1] (actual time=205..205 rows=1 loops=1)
    -> Filter: (grades.exam_score >= 65)  [est rows=9471] (actual time=1.66..205 rows=9577 loops=1)
        -> Table scan on grades  [est rows=776042] (actual time=1.63..172 rows=784000 loops=1)
```

**Reading it.** With no statistics the optimiser guessed that a range filter keeps one third of the table (258,655 rows). With the histogram it estimates 9,471, against an actual 9,577. The runtime did not change because there is no alternative access path here. A good estimate matters when the optimiser must choose between joins or indexes, as in Q7 and Q9.

## 12. Plan checklist used for every query

1. Is any large table read with `Table scan` when only a few rows are needed?
2. Do `[est rows]` and `actual rows` agree? If not, update statistics or add a histogram.
3. Is any node executed with a very large `loops` value (dependent subquery, re-planned range scan)?
4. Is the access `Covering index` where possible?
5. After adding an index, re-run the *other* queries. An index can change the plan of an unrelated query (section 10).
